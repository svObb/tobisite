# Превью-пайплайн: от карточки лида до живой страницы

Одна страница про то, как черновик сайта попадает в интернет и как оттуда
уходит. Код: `draft_service.py` (бот), `worker/src/index.ts` (раздача).

## Маршрут

```
карточка лида (leads + contacts + enrichment)
  → compose: рецепт, гейты, seed = sha256(domain_norm)
  → slot_gen: модель пишет тексты свободных слотов
  → render: HTML
  → checks.run_all: NAP, заглушки, скролл, a11y, форма
  → строка drafts (status=generated, slots_json, recipe_json)
  → резерв слага (status=publishing, r2_prefix)
  → PUT в R2: <slug>/index.html          ← публикация
  → строка drafts (status=published, r2_prefix, preview_host)
    и leads.draft_url = https://<slug>.tobisitepreview.com/
  → письмо со ссылкой на превью
```

Всё до PUT детерминировано seed'ом, кроме слот-генерации; поэтому тексты
слотов лежат в `drafts.slots_json` — повторная публикация собирает ту же
страницу, а не новую (модель второй раз не зовётся).

Тексты привязаны к версии библиотеки секций (`drafts.library_version`): ключ
слота — это «вариант.слот». Обновилась библиотека — `/publish` отказывается
публиковать старый черновик и просит пересобрать его, иначе часть страницы
уехала бы в интернет заготовками рецепта.

## Кто что запускает

| Шаг | Где | Чем |
|---|---|---|
| Сборка + публикация | бот | кнопка «Собрать черновик» в карточке лида |
| Повторная публикация | бот | `/publish <id лида>` — после сбоя R2 или правки карточки |
| Уборка превью | бот | на старте процесса и командой `/previews_gc` |
| Раздача страницы | Worker | `<slug>.tobisitepreview.com` → `<slug>/index.html` в R2 |
| Заявка с формы | Worker | POST `/api/lead` → сообщение в админ-чат |
| Открытия превью | Worker | POST `/api/hit` → Analytics Engine + объект в бакет |
| Разбор открытий | бот | фоновый опрос бакета раз в `PREVIEW_HITS_POLL_SEC` |

Ключи R2 (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`,
необязательный `R2_BUCKET`) живут в окружении бота, права токена — Object Read
& Write на бакет превью. Их нет — нет ни публикации, ни опроса открытий:
черновик остаётся в базе и в письме, а бот работает как раньше.

## Слаг

`tools/slugify_preview.py`: транслит названия компании в `[a-z0-9-]`, при
коллизии суффикс `-2`, `-3`. Точек в слаге нет намеренно — Universal SSL Free
покрывает ровно один уровень wildcard.

Слаг выдаётся один раз и остаётся за лидом навсегда, даже когда превью снято:
ссылка, сохранённая клиентом, не должна однажды открыть чужой сайт.

Закрепляется он **до** выкладки: строка черновика получает `r2_prefix` и
статус `publishing`, и только потом уходит PUT. Отсюда два свойства. Две
одновременные сборки компаний с одинаковым транслитом названия не получают
один слаг: у `drafts.r2_prefix` уникальный индекс, проигравший гонку берёт
следующий вариант. И объекта в бакете без строки о нём не остаётся: PUT идёт
после записи, а упавший PUT возвращает черновику статус `generated`, оставляя
слаг за ним, — `/publish` повторяет выкладку по тому же адресу.

## Открытия превью

У VPS бота нет наружных портов, и позвать его воркер не может. Поэтому канал
обратный: воркер кладёт каждое событие пустым объектом в тот же бакет, а бот
раз в две минуты забирает список и удаляет разобранное.

```
POST /api/hit {"event": "view"}
  → Analytics Engine (агрегаты, живут своей жизнью)
  → объект _hits/<slug>/<event>/<миллисекунды>-<нонс>, тело пустое
  → бот: list → preview_hits (строка на событие)
  → первое открытие: leads.preview_opened_at + сообщение админам и работнику
  → delete разобранного пачкой
```

Всё нужное лежит в имени ключа, поэтому опрос — это один `list` без единого
`GET`. Ни кук, ни адреса посетителя воркер не собирает, и передать их через
такой ключ нечем. Префикс `_hits/` слагом стать не может: подчёркивание не
проходит проверку слага.

Сообщение уходит **один раз** — при первом открытии (10.21, 10.22).
Дальнейшие события копятся в `preview_hits` молча: нажатие кнопки на превью и
без того приходит заявкой с формы.

Строки идут в базу по ключу объекта (`preview_hits.object_key` уникален), так
что не удалившийся объект не задваивает историю. Не записалось в базу —
объекты остаются в бакете до следующего захода.

## Срок жизни

- превью живёт 60 дней с публикации (`models.PREVIEW_TTL_DAYS`);
- превью закрытого лида (`refused`, `rejected`, удалён, отменён) снимается при
  первой же уборке;
- **превью проданного лида не снимается никогда** — из этой страницы делается
  боевой сайт.

Уборку делает бот, а не lifecycle-правило бакета: правило про статус лида
ничего не знает и снесло бы страницу проданного клиента. Правила на бакете —
только страховка: 180 дней на весь бакет (мусор от сбоев) и 7 дней на
префикс `_hits/` (хвосты, если поллер стоял).

Сняв превью, бот удаляет объекты под префиксом, ставит черновику статус
`expired` и убирает `leads.draft_url`: ссылка вела бы в 404.

Не удалось — превью остаётся `published` и попадёт в следующую уборку, а лид
уходит в строку «⚠️ Не вышло» отчёта `/previews_gc`. Неудача — это и отказ
базы, и ответ бакета `200` с `Errors` внутри: пока объект открывается,
превью считается живым.

## Проверка живого превью

```
python tools/preview_check.py https://<slug>.tobisitepreview.com/
```

Открывает страницу, шлёт тестовую заявку на `/api/lead` с заголовком
`X-Tobisite-Test: 1` (Worker проходит валидацию, но в чат не пишет) и меряет
скорость через PageSpeed mobile. Бюджет — LCP до 3 секунд.

Сеть настоящая, поэтому в CI и в `checks.run_all` этой проверки нет: там
работает только статическая `form_e2e.check`.
